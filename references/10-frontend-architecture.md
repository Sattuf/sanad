# المرحلة 10 — الواجهة الأمامية

## 10.1 القرار: تطبيق ويب واحد (React + TypeScript)، لا تطبيقين منفصلين

تطبيق React + TypeScript واحد (SPA)، متجاوب بالكامل، يخدم البوابات الثلاث (مستفيد، مختص، تنسيق) عبر توجيه قائم على الدور. Flutter يبقى خياراً صحيحاً لاحقاً بعد إثبات الفكرة، لا قراراً الآن.

## 10.2 حزمة التقنيات

| الطبقة | الاختيار | السبب |
|---|---|---|
| إطار العمل | React 18 + TypeScript + Vite | بناء سريع، دعم ممتاز لـ RTL |
| التوجيه | React Router v6 | توجيه متداخل حسب الدور |
| حالة الخادم | TanStack Query | Cache للاستعلامات |
| حالة العميل الخفيفة | Zustand | جلسة المستخدم والتفضيلات فقط |
| النماذج والتحقق | React Hook Form + Zod | يطابق DTOs الخلفية |
| عميل API | مولَّد من OpenAPI (`orval`) | مصدر حقيقة واحد |
| التصميم | Tailwind CSS + RTL | بساطة ونظافة بصرية |
| نظام تصميم | Storybook | اتساق مع نمو الفريق |
| الوقت الفعلي | `@microsoft/signalr` | يطابق SignalR Hub |
| الاختبار | Vitest + RTL + Playwright | وحدات + E2E |
| i18n | `i18next`، العربية وRTL افتراضياً | مطابق للسياق |
| الصوت | عنصر `<audio>` أصلي + مشغّل مخصص خفيف | لا حاجة لمكتبة ثقيلة لمقاطع قصيرة نسبياً (تلاوات/أدعية) |

## 10.4 شاشة الدخول الموحّدة (v3)

`/login` — ثلاثة أزرار متكافئة بصرياً، بلا أي حقل مستند:

```tsx
<AuthMethodPicker>
  <AuthButton method="email" />
  <AuthButton method="google" />     {/* يُحوَّل إلى /auth/google/challenge */}
  <AuthButton method="phone" />       {/* → إدخال رقم → OTP، خلف CAPTCHA */}
</AuthMethodPicker>
```

بعد أي طريقة ناجحة: دخول مباشر بدور `Beneficiary`، بلا أي شاشة وسيطة تطلب توثيقاً. زر "كن مقدّم خدمة" يظهر في `/dashboard` كدعوة اختيارية، لا خطوة إلزامية في مسار الدخول.

## 10.5 شاشة طلب الترقية (v3 — جديدة، تستبدل أي "تسجيل جهة" قديم)

`/provider-upgrade`:

```tsx
<UpgradeTypePicker>
  <TypeOption value="LicensedPhysician" label="طبيب مرخّص" />
  <TypeOption value="ReligiousPractitioner" label="شيخ / راقٍ شرعي" />
</UpgradeTypePicker>
{/* بعد الاختيار، نموذج المستندات يتغيّر ديناميكياً: */}
{selectedType === 'LicensedPhysician'
  ? <DocumentUpload accept="pdf,jpg,png" hint="شهادة/رخصة مزاولة طبية رسمية" />
  : <DocumentUpload accept="pdf,jpg,png" hint="إجازة أو تزكية من جهة شرعية معروفة" />}
```

النموذج يُرسَل كـ `RequestProviderUpgradeCommand` (راجع `03-application-layer.md` §3.2). الحالة بعد الإرسال: "طلبك قيد المراجعة" — لا تغيير فوري في الدور، متسقاً مع `06-core-modules-workflows.md` §6.1.

## 10.6 وحدة رعاية المستفيد (v3 — شاشتان منفصلتان تماماً بصرياً وبنيوياً)

هذا القسم الأهم في هذا الملف من الناحية الأخلاقية — الفصل البصري بين الشاشتين يجب أن يكون واضحاً بحيث لا يخطئ مختص أبداً بكتابة نص خاص في الحقل الموجَّه للمستفيد أو العكس.

```tsx
// features/patient-care/CaseNoteEditor.tsx  — بوابة المختص، لكل حجز
// شريط تحذير أحمر داكن ثابت أعلى المحرر: "ملاحظة إشرافية خاصة — لن يراها المستفيد أبداً تحت أي ظرف"
<CaseNoteEditor bookingId={id} />

// features/patient-care/RecommendationComposer.tsx  — بوابة المختص، لكل حجز
// شريط أخضر ثابت أعلى المحرر: "هذه التوصية سترسَل مباشرة للمستفيد الآن"
<RecommendationComposer bookingId={id}>
  <GuidanceTextArea placeholder="اكتب توجيهك للمستفيد..." />
  <TrackPicker source="publishedLibraryOnly" multiple />   {/* اختيار من المكتبة المنشورة فقط، لا رفع جديد هنا */}
  <SendButton />
</RecommendationComposer>

// features/patient-care/MyRecommendations.tsx — بوابة المستفيد
// قائمة زمنية للتوصيات المستلمة، كل توصية تعرض النص + مشغّل صوت مباشر لأي مقطع مقترَح
<MyRecommendationsList />
```

**قاعدة تصميم صارمة:** لا مكوّن واحد في نظام التصميم يجمع بين محرري §7.6/§10.6 في نفس الشاشة أو خلف نفس الزر — التمييز البصري (لون الشريط، النص التحذيري، الموضع في القائمة الجانبية) إلزامي ومراجَع في كل Pull Request يلمس هذين المكوّنين.

## 10.7 مكتبة الرقية والمشاركة (v3)

- `/library`: تصفح حسب التصنيف (تلاوات، أدعية، أذكار)، مشغّل صوت بسيط، زر "أضف للمفضلة"، زر "شارك" (ينشئ `SharedContentLink` ويعرض رابطاً قصيراً قابلاً للنسخ مباشرة).
- `/favorites`: قائمة تشغيل شخصية.
- `/public/shared/:shortCode` (خارج `app/router.tsx` المحمي — مسار عام بالكامل، بلا Route Guard): صفحة استماع بسيطة لمقطع واحد، مع دعوة لطيفة للتسجيل المجاني وتصفح المكتبة الكاملة. **لا يظهر فيها أي عنصر من واجهة المستخدم المصادَق** (لا شريط حساب، لا إشعارات) — صفحة مستقلة تماماً بتصميم أخف.

## 10.8 لا نظام تقييمات علني — بديلان اثنان الآن، لا واحد

- `ProviderCaseNote` (إشرافي، §10.6) — إشارة جودة داخلية لـ`Coordinator`/`ClinicalSupervisor` فقط.
- `ProviderRecommendation` (موجَّه للمستفيد، §10.6) — ليس تقييماً بل توجيهاً، اتجاهه معاكس تماماً لفكرة التقييم (من المختص إلى المستفيد، لا العكس).

لا حقل نجوم أو تقييم رقمي في أي منهما ولا في أي مكان آخر بالنظام.

## 10.9 بوابة الإدارة — إدارة الأدوار (v3)

`/admin/users` (`SystemAdmin` فقط): جدول المستخدمين، بحث بالبريد/الاسم، زر "منح دور" يفتح `<AssignRoleModal roles={['Coordinator','ContentManager','PrivacySecurityOfficer','ClinicalSupervisor']} />` — **لا يعرض خيار منح `SystemAdmin` من الواجهة إطلاقاً في هذا الإصدار** (يبقى محصوراً بآلية Bootstrap أو تدخل يدوي موثَّق خارج التطبيق نفسه، تفادياً لخطر تصعيد صلاحيات عرضي عبر واجهة).

## 10.10 مكوّنات السلامة المشتركة — بلا تغيير عن النسخة السابقة

`VerificationBadge`، `EmergencyReferralBanner` (يعرض الآن أيضاً عند رفض `SendProviderRecommendationCommand` بسبب مؤشر داخل رد الخطأ نفسه، إن وُجد)، `UnmonitoredChatWarning`، `AdministrativeDisclaimerFooter` — الفوتر يتضمن الآن أيضاً سطر "سند مجانية بالكامل، لا اشتراكات ولا خدمات مدفوعة".

## 10.11 اختبارات Playwright الحرجة (v3، مضافة على النسخة السابقة)

1. مختص يحاول كتابة توصية تحتوي "خذ 500 ملغ" → رفض واضح برسالة الفلتر، لا حفظ صامت.
2. مستفيد لا يرى أبداً زر أو مسار يؤدي لـ `CaseNoteEditor` أو محتواه، حتى بمحاولة وصول مباشر للرابط.
3. طلب ترقية بنوع "طبيب" ومستند "تزكية شرعية" → بعد المراجعة، حالة الطلب "مرفوض — عدم تطابق نوع المستند"، لا "قيد المراجعة" متعلّق.
4. فتح `/public/shared/:shortCode` من متصفح بلا أي جلسة أو كوكي سابق ينجح ويُشغّل المقطع.
5. جهة/مختص لا يظهر له أبداً أي عنصر واجهة يتعلق باشتراك أو دفع في أي شاشة.
